# ADR-004 · Where does the app store its data on the phone?

- **Status**: Accepted
- **Date**: 2026-11-25
- **Authors**: stepixels team

## Context

- This is the local storage ADR announced in ADR-002 and ADR-003.
- The course requires **local persistence that survives an app restart** [46–47], and the app must work **offline** [70–72].
- **The phone computes, the server saves** (ADR-003). The phone is the source of truth day to day: Supabase only keeps a copy, for users with an account.
- A **guest** (no account yet) has no data on Supabase: all their progress lives on the phone until they create an account.
- The data the app keeps:
  - small preferences: onboarding done, reset time, last community total;
  - **validations**: one record per validation (date, steps, pixels, image, sent or not). The revealed pixels, the finished images and the "days" of an image are computed from them. Supabase stores the same records (ADR-003);
  - the session token (already decided in ADR-003: SecureStore).
- The steps themselves are **not stored**: they are read from the phone each time the app opens. The images are JSON files shipped with the app, read only.
- A validation made offline must be **sent later, exactly once**.
- The team has two people and 5 days (November 23–27, 2026), demos with Expo Go on iOS, and follows the teacher's example repository (ADR-002).

## Decision

**SQLite** (`expo-sqlite`) with **Drizzle ORM** for the validations, **AsyncStorage** for the small preferences, and **SecureStore** for the session (ADR-003). This matches the course's "one storage per kind of data" table [63–64] and the teacher's example repository.

- The Drizzle schema lives in `src/db/schema.ts`. Migrations are generated by `drizzle-kit` into `src/db/migrations/` (never written by hand) and applied by the root layout at launch (`useMigrations`), as in `docs/conventions.md`.
- The local `validations` table has the **same columns as the Supabase table**. Each validation gets a **unique id created on the phone**. A `synced` flag marks the records not sent yet: they form the offline queue.
- Sending: right after a validation, then again when the app becomes active (`AppState`). The server ignores an id it already has, so a retried send never creates a duplicate.
- Sign-in on a new phone: the account's validations are downloaded into SQLite, replacing the guest's (the account wins). Sign-out: SQLite and the session are cleared; the reset time is kept.

Rejected:

- **expo-sqlite without Drizzle** (SQL written by hand) [65–66]: quicker to start, but no generated migrations and no TypeScript types for the rows, and `docs/conventions.md` would have to be rewritten.
- **AsyncStorage only** (one JSON object): the simplest, but the whole list is read and rewritten at each validation, the offline queue is fragile, and the course keeps AsyncStorage for small preferences.
- **`expo-sqlite/kv-store` instead of AsyncStorage**: one dependency less, but a gap with the course and the conventions for a small gain.
- **MMKV, WatermelonDB, PowerSync**: native modules (no Expo Go on iOS) or too big for the time we have.

## Consequences

- \+ Works offline and after a restart, for guests and for signed-in users.
- \+ Progress is never stored as a counter: it is computed from the validations, so the phone and the server cannot drift apart.
- \+ Same tools as the course [67] and the teacher's repository: setup copied from it, easier to explain and to review.
- \+ The offline queue is just a column (`synced`), and a unique id makes every send safe to retry.
- \- About half a day of setup: Drizzle migrations are `.sql` files, which need a Metro and Babel configuration to be bundled. Check the versions against Expo SDK 58 when installing.
- \- SQLite and AsyncStorage are **not encrypted**: never store a secret there. Only validations and preferences go there; the session stays in SecureStore.
- \- Two copies of the same table (SQLite and Supabase): a column change must be made on both sides, checked in review.
- \- A guest who uninstalls the app loses everything. This is accepted: the design asks for an account after the first finished image.
